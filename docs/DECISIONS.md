# S3Sport — سجل القرارات التقنية

## البيئة
- ASP.NET Core MVC على .NET 8 (مثبّت عبر `global.json` على SDK 8.0.425)، وEF Core 8.0.11 وSQL Server 2022.
- قاعدة البيانات: `S3SportDb`، والاتصال في `appsettings.json` → `ConnectionStrings:DefaultConnection`.

## قاعدة البيانات
| القرار | السبب |
|---|---|
| تسلسل المناطق: محافظة ← ولاية ← منطقة ← قرية | يطابق التقسيم الإداري في عُمان. الفرق ترتبط بـ **المنطقة** (`TeamAreas`) ويمكن أن تظهر في أكثر من منطقة، وتحدد منطقة واحدة رئيسية (فهرس فريد مُرشَّح). |
| `UserAreas` تخزن أعمق مستوى اختاره المستخدم | من يختار محافظة فقط يرى كل فرقها. يُسمح بمنطقة افتراضية واحدة لكل مستخدم (فهرس فريد مُرشَّح `IsDefault = 1`). |
| كل المفاتيح الأجنبية `RESTRICT` ما عدا حالات محددة | SQL Server يرفض مسارات الحذف المتعددة، وحذف البيانات الرياضية يجب أن يكون صريحاً. الحذف المتسلسل (Cascade) مقتصر على: `UserAreas`، `UserFollows`، `Notifications`، `PushSubscriptions` (عند حذف المستخدم)، و`TeamApplicationAreas`، و`MatchEventRevisions`. |
| الحذف المنطقي (Soft Delete) | يشمل: Teams، Players، Competitions، Venues، Matches، News، MediaFiles. يُطبَّق فلتر عام في الاستعلامات، و`SaveChanges` يحوّل الحذف إلى `IsDeleted = 1` تلقائياً. **ملاحظة:** الفريق المحذوف تختفي مبارياته من الاستعلامات، لذلك يُفضَّل **إيقاف** الفريق (Suspended) بدلاً من حذفه. |
| `RowVersion` | على: Team، Player، Competition، CompetitionSeason، TeamApplication، Match، MatchEvent، News. |
| الأوقات تُخزَّن بتوقيت UTC | وتُعرض بتوقيت مسقط (UTC+4). `KickoffAt` بتوقيت UTC. |
| `Competition` ← `CompetitionSeason` | البطولة كيان ثابت، ولكل موسم نسخة مستقلة تحمل النظام ونقاط الفوز والتعادل ومعايير كسر التعادل، ولذلك تبقى إحصائيات المواسم السابقة كما هي. |
| معايير كسر التعادل | تُخزَّن نصاً مرتباً (مثل `GoalDifference,GoalsFor,HeadToHeadPoints,Wins`) في `CompetitionSeason.TieBreakers`. |
| منع تكرار أحداث المباراة | لكل حدث `ClientRequestId` (Guid تولّده شاشة المسؤول عند كل ضغطة)، مع فهرس فريد على `(MatchId, ClientRequestId)`. |
| تصحيح الأحداث | لا تُحذف الأحداث، بل تُلغى (`IsCancelled`) أو تُعدَّل مع حفظ نسخة في `MatchEventRevisions`. تُعاد حساب النتيجة من الأحداث غير الملغاة. |
| المتابعة `UserFollows` | لكل نوع مفتاح أجنبي اختياري خاص به بدل معرّف عام (polymorphic) للحفاظ على سلامة العلاقات، مع قيد CHECK يفرض هدفاً واحداً فقط. |
| الإحصائيات مخزّنة مسبقاً | `CompetitionStandings` و`PlayerStatistics` و`TeamStatistics` لكل موسم، وتُعاد حسابها عند تغيّر النتائج. `GoalDifference` عمود محسوب. |
| `PushSubscriptions` | الجدول جاهز لإضافة Web Push لاحقاً. |
| المتابعة والإشعارات بلا شرط منطقة | المستخدم يتابع أي فريق أو لاعب أو بطولة أو مباراة من أي منطقة، ويشغّل أو يوقف إشعارات كل متابعة (`NotificationsEnabled`). زر المتابعة يكون في صفحة الفريق، وزر الجرس في صفحة تفاصيل المباراة. المنطقة تحدد فقط المحتوى المعروض افتراضياً. |
| أعمدة الإحصائيات خاصة بكرة القدم | الرياضات الأخرى تُضاف كسجلات في `Sports` و`SportPositions` دون تغيير البنية. الإحصائيات الخاصة برياضة معينة تُضاف لها جداول مستقلة عند الحاجة. |

## البيانات الأولية
- **مع الـ Migrations (`Data/SeedData.cs`):** 11 محافظة و61 ولاية، ورياضة كرة القدم ومراكزها الأربعة. قد لا تشمل القائمة ولايات استُحدثت مؤخراً، ويمكن إضافتها من لوحة الإدارة.
- **عند التشغيل (`Data/DbInitializer.cs`، وكل خطواته idempotent):**
  - الأدوار السبعة.
  - حساب SuperAdmin من إعداد `SeedAdmin`.
  - بيانات تجريبية عند تفعيل `Seed:DemoData`: 15 منطقة وقريتان والموسم الحالي.
- في بيئة التطوير: البريد وكلمة المرور في `appsettings.Development.json`. هذا الملف لا يُرفع إلى المستودع، وتنسخه من `appsettings.Development.example.json` وتضع فيه كلمة مرورك. في Production تكون `SeedAdmin` و`AutoMigrate` و`DemoData` فارغة أو معطلة افتراضياً.

## المرحلة الثانية: الحسابات والمناطق والفرق ولوحة الإدارة
| القرار | السبب |
|---|---|
| المنطقة الحالية تُخزَّن في كوكي `s3s_region` للجميع | الزائر يختار منطقته دون تسجيل. المستخدم المسجّل تُحفظ اختياراته أيضاً في `UserAreas`، ويُستعاد منها الكوكي عند تسجيل الدخول. |
| تحديد المنطقة يُبنى من **أعمق معرّف** مُرسَل | تُشتق المستويات الأعلى من قاعدة البيانات، فلا يمكن التلاعب بسلسلة المنطقة (`CurrentRegion.ResolveAsync`). |
| اختيار قرية يفلتر الفرق على مستوى منطقتها | الفرق مرتبطة بالمناطق (Areas)، والقرية تفصيل إضافي فقط. |
| عدم استخدام DevExtreme DataGrid | يتطلب ترخيصاً تجارياً مدفوعاً. استُبدل بجداول تعمل من جهة الخادم: بحث وفلترة وترتيب وتقسيم صفحات (`PagedResult` و`_Pager`)، وهي أخف وتعمل بدون JavaScript. |
| المكتبات محلية في `wwwroot/lib` | تشمل Bootstrap 5.3.3 RTL وFont Awesome 6.5.2 وSweetAlert2 11.12.4 وChart.js 4.4.4، فلا اعتماد على CDN عند النشر على IIS، وهو ضروري لـ PWA لاحقاً. الخط IBM Plex Sans Arabic من Google Fonts، مع خطوط النظام كبديل. |
| ترقية Bootstrap من 5.1 إلى 5.3.3 | لدعم الوضع الليلي والنهاري عبر `data-bs-theme`. |
| الموافقة على الطلب تتم في Transaction واحدة | تشمل: إنشاء الفريق ومناطقه وعضوية المسؤول ومنح دور TeamManager والإشعار وسجل العمليات. تُستخدم `InTransactionAsync` لأن استراتيجية إعادة المحاولة في SQL Server لا تسمح بـ Transactions يدوية بدونها. |
| حماية التعديل المتزامن | تُرسَل `RowVersion` مع النماذج، وأي قيمة قديمة أو تالفة تُعامل كتعارض ولا تسبب خطأ 500. |
| رفع الصور | يُتحقق من الامتداد والحجم (2MB) والبصمة الثنائية (magic bytes)، ويُحفظ الملف باسم عشوائي في `uploads/`. تُرسل الملفات المرفوعة مع ترويسة `X-Content-Type-Options: nosniff`. |
| النصوص العربية تُخرج كما هي في HTML وJSON | بدل ترميزها كـ `&#x...;`، مما يقلل حجم الصفحات. الرموز الحساسة في HTML ما زالت تُرمَّز. |
| إيقاف الحساب أو تغيير صلاحياته يحدّث `SecurityStamp` | ويُتحقق منه كل دقيقة، فيُطبَّق التغيير على المستخدم المتصل خلال دقيقة. |
| حماية حسابات المدراء | لا يمنح أو يسحب دوري SuperAdmin وAdmin إلا SuperAdmin. لا يمكن لأي مدير إيقاف حسابه أو سحب دور SuperAdmin من نفسه. |
| دور TeamManager يُدار تلقائياً | يُمنح عند الموافقة على طلب الفريق أو عند الإضافة كمسؤول فريق، ويُسحب عند إزالة المستخدم من آخر فريق يديره. |
| المنطقة المقترحة في طلب الفريق | إذا لم يجد مقدم الطلب منطقته في القائمة يكتب اسمها، فيُحفظ في `ProposedAreaName` ويبقى `AreaId` فارغاً، مع قيد CHECK يشترط وجود أحدهما. عند الموافقة تُنشأ المنطقة تحت الولاية، ويمكن للأدمن تصحيح الاسم العربي وإضافة الإنجليزي. إذا كان الاسم موجوداً مسبقاً في الولاية تُستخدم المنطقة الموجودة ولا تُكرر، سواء عند التقديم أو عند الموافقة. نموذج الأدمن لإضافة فريق ما زال يتطلب اختيار منطقة مسجلة. |
| الفريق الذي له مباريات لا يُحذف | يُوقف بدلاً من ذلك للحفاظ على سجل النتائج. |
| إزالة `MultipleActiveResultSets` من الاتصال | التطبيق لا يحتاجها، وكانت تعطّل نقاط الحفظ (savepoints) داخل الـ Transactions. |

## واجهة المستخدم العادي: الفرق والمتابعة والمفضلة
| القرار | السبب |
|---|---|
| صفحة الفرق `/Teams` تعرض فرق منطقة المستخدم افتراضياً | مع زر لعرض كل المناطق، وبحث بالاسم أو الولاية أو المنطقة. |
| صفحة الفريق برابط مقروء `/teams/{slug}` | الفرق الموقوفة تُرجع 404 للزوار، ويستطيع المدير رؤيتها. |
| رقم هاتف الفريق لا يُعرض للعامة | هو رقم مقدم الطلب الشخصي. تُعرض البيانات العامة فقط: البريد ورابط التواصل الاجتماعي. |
| المتابعة بلا شرط منطقة | تُتاح لأي فريق أو لاعب أو بطولة أو مباراة من أي منطقة، مع مفتاح إشعارات لكل متابعة تكون مفعّلة افتراضياً. تكرار طلب المتابعة لا يُنشئ صفاً ثانياً بفضل الفهرس الفريد. |
| المتابعة بدون إعادة تحميل الصفحة | يعيد الخادم رسم جزء أزرار المتابعة `_FollowButton`، فلا يتكرر منطق العرض في JavaScript. عند فشل fetch يُرسل النموذج بالطريقة العادية، فتعمل المتابعة حتى بدون JavaScript. |
| الصفحة الرئيسية تعرض "فرقي المفضلة" من أي منطقة | ثم فرق المنطقة، ثم "الأكثر متابعة" في المنطقة. إذا لم يوجد في المنطقة فرق متابَعة تُعرض قائمة عُمان كلها. |

## المرحلة الثالثة: اللاعبون والبطولات والجدولة والترتيب
| القرار | السبب |
|---|---|
| الانتقال بين فريقين يسجّله الأدمن فقط | لأنه يمس فريقين. مسؤول الفريق يضيف لاعبين جدداً، ويضم لاعباً حراً، ويُنهي ارتباط لاعب بفريقه. كل حركة تُحفظ في `TeamPlayers` و`PlayerTransfers`، ولا يُحذف تاريخ اللاعب. |
| لاعب واحد في فريق نشط واحد | يضمنه فهرس فريد مُرشَّح. وفي كل حركة يُغلق الارتباط القديم أولاً ثم يُفتح الجديد داخل نفس الـ Transaction. |
| مسؤول البطولة يرى البطولات المسندة إليه فقط | الإسناد عبر `CompetitionManagers`. ويُمنح دور TournamentManager ويُسحب تلقائياً عند الإسناد والإزالة. |
| الجدولة التلقائية للدوري والمجموعات | بطريقة الدائرة (round-robin): كل فريق يقابل الجميع، مع توزيع متوازن للعب على الأرض، ودعم الذهاب والإياب. |
| توزيع المجموعات | بطريقة «الأفعى» حسب التصنيف، أو بقرعة عشوائية. |
| خروج المغلوب بأي عدد من الفرق | يُكمَّل العدد إلى أقرب قوة للعدد 2، وتحصل الفرق الأعلى تصنيفاً على تأهل مباشر (bye). صاحب التأهل المباشر يقابل فائزاً من الطرف المقابل للقرعة، فلا يلتقي المصنفان الأول والثاني مبكراً. |
| المتأهلون من المجموعات (النظام المختلط) | ترتيبهم: أوائل المجموعات ثم الثواني. الأول يقابل ثاني مجموعة أخرى، فلا يلتقي فريقان من نفس المجموعة قبل الأدوار المتقدمة. |
| مسار خروج المغلوب يُعاد اشتقاقه دائماً | من المجموعة الأولى ونتائج كل دور، فلا تُخزَّن بيانات إضافية للتأهلات المباشرة. والبطل يُحدَّد من هذا المسار عند بقاء فريق واحد، وليس من اسم الدور القابل للتعديل. |
| الترتيب والإحصائيات تُعاد حسابها بالكامل | لكل نسخة بطولة بعد كل نتيجة أو تصحيح، فيبقى التصحيح صحيحاً دائماً. تعديلات النقاط اليدوية (خصم أو إضافة) تبقى محفوظة بعد إعادة الحساب. |
| الإحصائيات تُحسب من المباريات المنتهية فقط | المباريات الجارية لا تدخل في الترتيب ولا في الهدافين حتى تنتهي. |
| معايير كسر التعادل يختارها المنظم بالترتيب | الخيارات: فارق الأهداف، الأهداف المسجلة، المواجهات المباشرة (النقاط، الفارق، الأهداف)، عدد الانتصارات، اللعب النظيف. وإذا تساوت كلها يُرتَّب الفريقان أبجدياً. |
| إدخال النتيجة يدوياً للمباريات غير المغطاة مباشرة | متاح من نموذج المباراة. ويُشترط إدخال ركلات الترجيح بدون تعادل في المباراة الإقصائية المتعادلة. |
| ثقافة `ar-OM` بإشارات ASCII | ICU يستخدم «؜-» و«٫» فتفشل قراءة `-2` و`23.58` القادمة من النماذج وتصبح 0 دون أي رسالة. تم استبدالها بالرموز التي يرسلها المتصفح. |

## المرحلة الرابعة: إدارة المباراة المباشرة
| القرار | السبب |
|---|---|
| الحالة والنتيجة تُشتقّان دائماً من الأحداث غير الملغاة | الحالة: لم تبدأ، مباشر، استراحة، انتهت. النتيجة: الأهداف، والهدف العكسي يُحسب للخصم. لذلك تبقى النتيجة صحيحة بعد أي تصحيح أو إلغاء. |
| كل كتابة على المباراة داخل Transaction | مع قفل على صف المباراة (`UPDLOCK`)، فتُنفَّذ طلبات أكثر من مسؤول بالتتابع. اختُبر بإرسال 5 أهداف متزامنة، فحُسبت كلها بدون أي فقد. |
| منع التسجيل المكرر | لكل ضغطة `ClientRequestId`، ويُعاد استخدامه عند إعادة المحاولة بعد خطأ شبكة. فحص قبل الحفظ، مع فهرس فريد كحماية أخيرة. اختُبر بإرسال 5 طلبات متطابقة متزامنة، فحُفظ حدث واحد فقط. |
| التصحيح والإلغاء لا يحذفان | كل تعديل يُحفظ في `MatchEventRevisions` بالقيم القديمة والجديدة والسبب ومن قام به. يمكن التراجع عن آخر تغيير في حالة المباراة فقط، مثل نهاية مباراة أُعلنت بالخطأ. |
| تسلسل الحالة إلزامي | البداية ← نهاية الشوط الأول ← بداية الشوط الثاني ← النهاية. في الاستراحة يُسمح بالتبديلات فقط. |
| SignalR يرسل بعد الحفظ في قاعدة البيانات | مجموعة لكل مباراة، ومجموعة `live` لقوائم النتائج، والإشعارات الشخصية تُرسل للمستخدم مباشرة. فشل الإرسال لا يُفشل تسجيل الحدث. |
| إشعارات المباراة | تُرسل لمن يتابع المباراة أو أحد الفريقين. كتم المباراة يُسكتها حتى لو كان الفريق متابَعاً. الأحداث المُرسلة: البداية، الأهداف، نهاية الشوط الأول، النهاية، تغيير الموعد أو التأجيل. البطاقات لا تُرسل. |

## المرحلة الخامسة: الواجهة العامة والأخبار وPWA
| القرار | السبب |
|---|---|
| مركز المباريات | بالأيام (اليوم ±3)، مع تبويب «مباشر»، وتجميع حسب البطولة. الدقيقة والنتيجة تتحدثان مباشرة في كل الصفحات عبر `live.js`. |
| صفحة المباراة | تتحول تلقائياً إلى العرض المباشر عند بدء المباراة. فيها الأحداث والتشكيلة والمعلومات والمواجهات السابقة. وعند تعذّر WebSockets تتحدث بالاستطلاع كل 30 ثانية. |
| نص الخبر نص عادي | بدون HTML، فلا مجال لحقن سكربتات. |
| الفيديو من يوتيوب فقط | يُعرض عبر `youtube-nocookie` باستخدام معرّف الفيديو وحده. |
| النشر الأول للخبر يرسل إشعاراً | لمتابعي الفريق أو اللاعب أو البطولة المرتبطة، أو فريقي المباراة. إعادة حفظ خبر منشور لا تكرر الإشعار. |
| PWA | Service Worker: الملفات الثابتة من التخزين المؤقت أولاً، والصفحات من الشبكة أولاً. **الصفحات العامة فقط** تُحفظ للقراءة دون اتصال؛ المفضلة والإشعارات والحساب لا تُحفظ أبداً. يتضمن معالج `push` جاهزاً لتفعيل Web Push لاحقاً. |
| شريط تنقّل سفلي في الهاتف | الرئيسية، المباريات، البطولات، الترتيب، المفضلة. |

| ملفات لا تُنشر | `appsettings.Development.json` و`App_Data`. |

## مباريات الفرق الودية والتسجيل المباشر من مسؤول الفريق
| القرار | السبب |
|---|---|
| مسؤول الفريق يضيف **المباريات الودية** فقط | مباريات البطولات يجدولها ويسجّلها مسؤول البطولة أو المسؤول المعيّن، لأن نتيجتها تؤثر على الترتيب. لو سجّلها أحد الفريقين لكان طرفاً وحكماً في نفس الوقت. |
| الحقل `Match.OrganizerTeamId` | يحدد الفريق المنظِّم. مسؤولو هذا الفريق فقط يعدّلون المباراة ويسجّلونها مباشرة، ومسؤول الفريق الخصم لا يستطيع. يضمن قيد `CK_Matches_Organizer` أن المباراة ودية وأن المنظِّم أحد طرفيها. |
| الخصم من المنصة أو «فريق ضيف» يُكتب اسمه | أغلب المباريات الودية المحلية تكون ضد فرق غير مسجلة. الفريق الضيف حالته `TeamStatus.Guest`، فلا يظهر في قوائم الفرق ولا يمكن متابعته، وصفحة المباراة لا تضع رابطاً له. إذا كُتب نفس الاسم مرة أخرى يُستخدم الفريق الضيف نفسه. |
| التعديل والحذف قبل البداية فقط | بعد أول حدث تُدار المباراة من شاشة التسجيل، وتُصحَّح الأحداث هناك مع حفظ سجل التعديلات. |
| إشعار لكل حدث مباشر | يصل لمتابعي المباراة أو أحد الفريقين: البداية، الأهداف (عادي، جزاء، عكسي)، الجزاء الضائع، البطاقات، التبديلات، نهاية الشوط الأول، بداية الشوط الثاني، والنهاية. يتضمن الإشعار اسم اللاعب والدقيقة المحفوظة. كتم إشعارات المباراة يوقفها كلها. |
| إشعار عند إضافة مباراة ودية | يصل لمتابعي الفريقين. |
| لاعبو الفريق الضيف أسماء مكتوبة | الفريق الضيف ليس له لاعبون مسجلون، فتُكتب أسماء لاعبيه في الحدث نفسه في الحقلين `PlayerNameText` و`RelatedPlayerNameText`. يمكن بذلك تسجيل التبديلات والأهداف والبطاقات بأسماء اللاعبين دون إنشاء لاعبين يظهرون في القوائم العامة. |
| اللاعب غير المسجل: رقم القميص أو الاسم، واختياري | كثير من الخصوم لا يسجلون لاعبيهم. لذلك يقبل أي حدث (هدف، بطاقة، تبديل) رقم القميص أو اسماً مكتوباً بدل لاعب من القائمة، أو لا شيء. الرقم وحده يُحفظ «رقم 7». إذا لم يكن للفريق لاعبون مسجلون يظهر مربع نص فقط، ويُقبل التبديل دون أسماء. وإذا كان له لاعبون تظهر القائمة، وفي آخرها «لاعب غير مسجل» لمن ليس فيها، ويبقى التبديل محتاجاً للاعبَين (من القائمة أو مكتوبَين). إذا اختير لاعب من القائمة يتجاهل الخادم النص، حتى تبقى الإحصائيات مرتبطة باللاعبين الحقيقيين. الأسماء المكتوبة لا تدخل في إحصائيات الهدافين. |

## التسجيل: مستخدم عادي أو فريق
| القرار | السبب |
|---|---|
| «حساب جديد» يبدأ باختيار نوع الحساب | المستخدم العادي يكتب بيانات حسابه فقط. الفريق يكتب بيانات الحساب وبيانات الفريق معاً في صفحة واحدة: الاسم، والمنطقة، والشعار، ورقم التواصل. |
| الحساب وطلب الفريق في عملية واحدة | يُنشآن داخل transaction واحدة، فإما يُحفظان معاً أو لا يُحفظ شيء. لا يبقى حساب بلا طلب، ولا يُخزَّن شعار لمحاولة فاشلة، لأن شروط كلمة المرور تُفحص قبل حفظ الشعار. |
| نفس قواعد طلب الفريق | التحقق والحفظ في `TeamFormHelper.ValidateApplicationAsync` و`MapApplication`، يستخدمهما التسجيل كفريق وطلب الفريق من داخل الحساب معاً. |
| الفريق ينتظر موافقة الإدارة | الحساب الجديد يبدأ «مستخدماً»، ويصبح «مسؤول فريق» عند الموافقة، فلا ينتحل أحد اسم فريق. البريد المسجل مسبقاً يُوجَّه لتسجيل الدخول وتقديم الطلب من حسابه. |
| الصلاحيات فور الموافقة (`RoleRefresh`) | الصلاحيات محفوظة في ملف تعريف الدخول. أي إجراء يغيّر صلاحيات مستخدم يعلّم حسابه، وهي: الموافقة على فريق، وإضافة مسؤول فريق أو إزالته، وتعيين مسؤول بطولة، وتعديل الأدوار. في أول طلب تالٍ من ذلك المستخدم يُعاد إصدار ملف دخوله بالصلاحيات الجديدة، بدون تسجيل خروج. التعليم في الذاكرة لأن التطبيق يعمل على خادم واحد، وفحص الـ security stamp كل دقيقة يغطي ما قد يفوت. |
| مسؤول الفريق يتحكم بكل شيء في فريقه فقط | يعدّل الاسم والشعار والبيانات، ويضيف اللاعبين ويعدّلهم ويحذفهم، ويُنهي ارتباطهم، ويضيف المباريات الودية ويعدّلها ويحذفها ويسجّلها مباشرة. كل إجراء يتحقق من أنه مسؤول عن هذا الفريق تحديداً، والاختبارات تتأكد أن صفحات الفرق الأخرى وبياناتها مرفوضة له. |
| تغيير المنطقة وحذف الفريق للإدارة | المنطقة تحدد بطولات المنطقة التي يظهر فيها الفريق، وحذف فريق له مباريات يمسّ ترتيب الفرق الأخرى ونتائجها. |
| حذف اللاعب للمضاف بالخطأ فقط | اللاعب الذي له أي سجل يبقى، ويُنهي المسؤول ارتباطه بدلاً من حذفه، حتى لا تختل إحصائيات المباريات والفرق الأخرى. السجل يشمل: أحداث المباريات، والتشكيلات، وجائزة أفضل لاعب، والارتباط بفريق آخر. الحذف soft delete. |

## إشعارات الجهاز (Web Push)
| القرار | السبب |
|---|---|
| مكتبة `WebPush` مع مفاتيح VAPID | المعيار المدعوم في Chrome وEdge وFirefox وأندرويد وSafari (على آيفون بعد إضافة الموقع إلى الشاشة الرئيسية). يرسل الخادم الإشعار مباشرة لخدمة الإشعارات في المتصفح دون الحاجة لحساب Firebase. |
| مفاتيح VAPID ثابتة | تُقرأ من الإعدادات `WebPush:PublicKey` و`WebPush:PrivateKey`، وإن لم توجد تُولَّد مرة واحدة وتُحفظ في `App_Data/vapid.json`. تغيير المفاتيح يُبطل اشتراكات الأجهزة، والجهاز يعيد الاشتراك تلقائياً في زيارته التالية. |
| صندوق صادر (Outbox) | كل إشعار يُحفظ مع `PushPending = 1`، وتتولى خدمة خلفية (`PushWorker`) إرساله ثم تُصفّر العلامة. بهذا لا ينتظر مسؤول المباراة خدمات الإشعارات الخارجية، وتشمل الإرسال كل الإشعارات أينما أُنشئت. عند الحفظ تُوقَظ الخدمة فوراً، وإلا تفحص كل 3 ثوانٍ. |
| لا يُرسل إشعار قديم | الإشعار الذي مضى عليه أكثر من 15 دقيقة لا يُرسل للجهاز، مثلاً بعد توقف الخادم، لأن «هدف!» بعد ساعة يضلّل. الإشعارات القديمة قبل هذه الميزة لا تُرسل أيضاً، لأن الـ migration يضعها `PushPending = 0`. |
| حذف الاشتراكات المنتهية | إذا ردّت خدمة الإشعارات بـ 404 أو 410 (الاشتراك انتهى)، أو 401 أو 403 (تغيّر المفتاح)، يُحذف الاشتراك. |
| قبول خدمات الإشعارات المعروفة فقط | الخادم يرسل طلباً إلى العنوان الذي يسجّله المتصفح، لذلك لا يُقبل إلا HTTPS على نطاقات Google وMozilla وMicrosoft وApple، وإلا أمكن استغلاله لجعل الخادم يتصل بعناوين داخلية (SSRF). |
| جهاز واحد لحساب واحد | إذا سجّل مستخدم آخر الدخول على نفس الجهاز ينتقل الاشتراك إليه. عند تسجيل الخروج يُلغى اشتراك الجهاز، فلا تصل إشعارات حساب لشخص آخر. |
| طلب الإذن بعد أول متابعة | يُعرض طلب الإذن بعد أول متابعة مرة واحدة فقط، ويمكن التفعيل أو الإيقاف في أي وقت من صفحة الإشعارات. المتصفحات تمنع طلب الإذن دون نقرة من المستخدم. |
| كتم الإشعارات يشمل الجهاز | الإشعار المكتوم لا يُنشأ أصلاً، فلا يُرسل للجهاز. |

## تنظيم الكود
- النماذج مجمّعة حسب الوحدة في ملفات: `Models/Regions.cs`، `Teams.cs`، `Players.cs`، `Competitions.cs`، `Matches.cs`، `Statistics.cs`، `Content.cs`، `Engagement.cs`.
- إعدادات Fluent API في `Data/Configurations/*`.
- أدوات مساعدة ثابتة (ليست Services) في `Infrastructure/`، من أهمها:
  - الأساس: `CurrentRegion` و`FileUploadHelper` و`OwnershipHelper` (صلاحيات الملكية).
  - البطولات: `FixtureGenerator` (خوارزميات الجدولة) و`StandingsCalculator` و`EditionHelper`.
  - المباريات والمتابعة: `MatchLiveHelper` و`NotificationHelper` و`FollowHelper` و`PlayerHelper`.
- لوحة الإدارة في `Areas/Admin`. كل Controller محمي بالسياسة المناسبة لدوره، مع تحقق ملكية داخل كل إجراء.
- SignalR في `Hubs/LiveHub.cs`. سكربتات الواجهة في `wwwroot/js`: `site.js` و`live.js` و`match.js` و`operator.js`، والـ Service Worker في `wwwroot/sw.js`.
- اختبارات شاملة (end-to-end) في `tests/e2e`، والتفاصيل في `tests/e2e/README.md`.
- لا يوجد Repository أو Service Pattern؛ الـ Controllers تستخدم `ApplicationDbContext` مباشرة.
- حماية CSRF مفعّلة عامةً عبر `AutoValidateAntiforgeryTokenAttribute`.

| تنبيه خاص عند فتح الرابط من داخل إنستغرام أو فيسبوك أو سناب أو تيك توك | المتصفح الداخلي في هذه التطبيقات لا يدعم التثبيت، فيُطلب من المستخدم فتح الرابط في المتصفح أولاً. |
| زر الإغلاق يخفي الشريط 7 أيام (في تخزين المتصفح). لا يظهر أي شيء داخل التطبيق المثبت | حتى لا يزعج الزائر، وحتى لا يُطلب التثبيت ممن ثبّت التطبيق. |

## نوع المباراة عند مسؤول الفريق (ودية أو بطولة)

| القرار | السبب |
|---|---|
| حقل «نوع المباراة» اختياري، والافتراضي «ودية». إذا اختار «بطولة» يظهر حقل «اسم البطولة» ويصير مطلوباً | طلب صاحب المنصة. أغلب مباريات الفرق ودية، فما نزيد خطوة على المسؤول. |

| الرجوع إلى «ودية» يمسح الاسم | ما يبقى اسم بطولة مخفي على مباراة ودية. |
